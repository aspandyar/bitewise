# Этап 3 — `ft/diary`: дневник, приёмы пищи, итоги дня

Дата: 2026-10-11 · Статус: реализовано · Ветка: `ft/diary` (от `master`)

## Цель
Пользователь записывает, что съел, по приёмам пищи и видит, сколько съедено и сколько осталось до нормы ккал/БЖУ. Запись приёма — не дольше 15 секунд.

**Готово, когда:** добавил запись по граммам и по порции, изменил, удалил — итоги дня и полоски прогресса пересчитались; можно ходить по дням (вчера, позавчера, обратно к сегодня). `pnpm lint` и `pnpm test` зелёные, CI зелёный.

## Принятые решения
| Вопрос | Решение | Почему |
| --- | --- | --- |
| Что такое «сегодня» | часовой пояс браузера в cookie `tz`; сервер считает дату в нём; без cookie — `DEFAULT_TIME_ZONE = "Asia/Almaty"` из config | UTC сдвигает ночной перекус во «вчера» (в Алматы до 05:00); без миграции, поездки подхватываются сами |
| Еда после полуночи | пока — через навигацию: «← вчера» → «+» | автоматику (граница дня в 04:00 или кнопка «во вчера») решим после недели жизни с дневником |
| Порции в записи | запись хранит снимок порции (название, граммы) и количество; граммы = количество × граммы порции; ввод в граммах тоже есть | в дневнике видно «2 шт (120 г)»; правка или удаление порции у продукта не меняет прошлые записи |
| Снимок нутриентов | в записи — значения продукта **на 100 г** на момент добавления + граммы; итоги считает `lib/nutrition.ts` | правка граммов пересчитывается точно от тех же чисел, без накопления округлений; история не зависит от правки продукта |
| Название в записи | снимок `food_name` | переименование продукта не переписывает историю |
| Поток добавления | отдельные экраны: поиск → количество → день | системное «назад» работает естественно; серверные компоненты + один клиентский поиск |
| Живой итог при вводе граммов | нет | `ui.md`: клиент сам нутриенты не считает; ккал на порцию показывает сервер |
| Смена порции в правке | нельзя: в правке меняется количество порций снимка или переход на граммы; другая порция — удалить и добавить | снимок остаётся честным, правка проще |
| Удаление записи | настоящее (`DELETE`) | на запись никто не ссылается, в отличие от продукта |
| Будущие даты | запрещены; «→» на сегодня неактивна | план питания — отдельная фича (Tier 4) |

## Отступления при реализации
- `updateEntry` и `deleteEntry` возвращают `{ date } | null` (а не boolean): после действия редирект ведёт на день записи.
- Формы (`addEntryFormSchema`, `updateEntryFormSchema`) не содержат `date` и `foodId`: они проверяются отдельно (`parseDiaryDate`, `parseId`), неверные → 404.
- `FoodSearch` получает объект `link: { prefix, search }`, а не функцию `hrefFor` — функцию нельзя передать из серверного компонента в клиентский.
- Индекс `diary_entries_food_id_idx` — для проверки FK при каскадном удалении продуктов пользователя.
- После ревью: общий лимит `DIARY_LIMITS.maxEntriesTotal` (100 000) и `pg_advisory_xact_lock` на пользователя в `addEntry` — иначе скрипт перебирает даты и пишет ~1 млн строк, а параллельные запросы обходят лимиты.
- После ревью: формы добавления и правки и поиск перемонтируются по `key` (дата, приём, число записей дня; сохранённые значения записи) — `cacheComponents` хранит скрытые экраны с состоянием, и форма подставляла прошлый приём пищи или откатывала граммы.
- После ревью: при переключении «Порции → Граммы» поле граммов заполняется `calcPortionGrams` (граммы, не нутриенты).

## Вне этапа
- Рецепты в дневнике (этап 4).
- Избранное, недавние, «повторить приём», «просто N ккал» без продукта (этап 5) — для последнего таблица доработается миграцией.
- Несколько норм и выбор нормы на день (`day_settings`).
- Перенос записи на другой день.
- Клетчатка и источник записи (`source`: manual / barcode / ai…) — добавятся миграцией с default на этапах 7 и 10.
- Граница дня после полуночи, живой итог при вводе — в открытые вопросы `notes.md`.

## Данные (`db/schema.ts`, через `/db-change`)
Одна сгенерированная миграция: enum `meal` и таблица `diary_entries`.

`meal` (enum, кортеж `MEALS` в `config.ts`): `breakfast`, `lunch`, `dinner`, `snack` — в этом порядке и выводятся.

### `diary_entries`
| Поле | Тип | Примечание |
| --- | --- | --- |
| id | uuid pk default random | |
| user_id | uuid not null → users, on delete cascade | индекс `(user_id, date)` — день читается одним запросом |
| date | date not null | локальная дата пользователя |
| meal | meal not null | |
| food_id | uuid not null → foods (no action) | продукты удаляются только мягко, ссылка не рвётся; при удалении пользователя каскад users → foods и users → diary_entries проходит в одном операторе |
| food_name | text not null | снимок названия |
| kcal_100, protein_100, fat_100, carbs_100 | numeric(8,2) not null | снимок «на 100 г», углеводы без клетчатки |
| grams | numeric(8,2) not null | сколько съедено |
| portion_label | text null | снимок порции |
| portion_grams | numeric(8,2) null | |
| portion_count | numeric(8,2) null | |
| created_at, updated_at | timestamptz not null default now() | порядок записей в приёме — `created_at`, затем `id` |

CHECK:
- `grams > 0`;
- нутриенты `>= 0`;
- порция целиком: `(portion_label IS NULL) = (portion_grams IS NULL) AND (portion_grams IS NULL) = (portion_count IS NULL)`;
- `portion_grams > 0`, `portion_count > 0`, если заданы.

`grams = portion_count × portion_grams` обеспечивает код, не CHECK: после округления до сотых равенство было бы хрупким.

**Риски миграции:** новые пустые enum и таблица, блокировок и потери данных нет.

### Доступ (каждый запрос репозитория)
- Запись видна и меняется только при `user_id` = пользователь сессии; иначе «не найдено» (404).
- Добавить можно только видимый пользователю продукт (`visibleTo` из `lib/foods/repo.ts`) и только видимую порцию **этого** продукта (общая или своя).

### Лимиты (`DIARY_LIMITS` в `config.ts`)
- граммы: 0,1–5000 (как у порции);
- количество порций: 0,25–50, кнопки −/+ с шагом 0,5;
- записей в день: не больше 100 (защита от скриптов; две одновременные отправки могут дать 101 — это UX-лимит);
- дата: от 2000-01-01 до «сегодня» пользователя включительно.

## Расчёты (`lib/nutrition.ts`, тест первым)
- `calcEntryNutrients(per100, grams)` → `{ kcal, proteinG, fatG, carbsG }`, каждое = значение_на_100 × grams / 100. 0 г → нули. Отрицательные и NaN → `RangeError`.
- `calcPortionGrams(portionGrams, count)` → граммы; `portionGrams` и `count` должны быть > 0.
- `sumNutrients(list)` → сумма; пустой список → нули.
- `calcDayProgress(target, eaten)` → для `kcal`, `proteinG`, `fatG`, `carbsG`: `{ eaten, target, remaining, share }`, где `remaining = target − eaten` (отрицательное — перебор), `share = eaten / target` без обрезки. Ширину полоски до 100 % обрезает UI.
- Без округления; округляет только вывод (`lib/format.ts`).

## Дата (`lib/date.ts`, чистые функции)
- `todayInTimeZone(now: Date, timeZone: string): IsoDate` — через `Intl.DateTimeFormat`.
- `addDays(date: IsoDate, days: number): IsoDate` — через UTC, без сдвига часового пояса.
- `isValidTimeZone(value: string): boolean`.
- Существующий `todayIsoDate` (UTC, для возраста) не меняется.

**Cookie пояса:**
- `components/time-zone-cookie.tsx` (клиентский, в корневом layout): если cookie `tz` нет или она не совпадает с `Intl.DateTimeFormat().resolvedOptions().timeZone` — ставит `tz` (`path=/`, год, `SameSite=Lax`) и вызывает `router.refresh()`. Мигнёт один раз при первом визите или смене пояса.
- `lib/diary/today.ts` → `getUserToday(now)`: читает cookie через `cookies()`, проверяет `isValidTimeZone`, иначе `DEFAULT_TIME_ZONE`.

## Вывод (`lib/format.ts`)
- `formatAmount(count)` — «1», «1,5», «0,25» (запятая, без лишних нулей).
- `formatDayLabel(date, today)` — «Сегодня», «Вчера», иначе «9 окт, пт» (`Intl`, `ru`; год — если не текущий).

## Серверная логика
**`lib/diary/schema.ts`** (zod, общие для форм и сервера):
- `mealSchema`, `isoDateSchema` (формат + реальная дата), `parseDiaryDate(value, today)` — дата в пределах лимитов, иначе null;
- `addEntrySchema`: `date`, `meal`, `foodId` (uuid), `amount` — union `{ mode: "grams", grams }` | `{ mode: "portion", portionId, count }`;
- `updateEntrySchema`: `meal`, `amount` — `{ mode: "grams", grams }` | `{ mode: "portion", count }`;
- числа принимают запятую (`decimalField`).

**`lib/diary/repo.ts`:**
- `getDayEntries(db, userId, date)` → записи дня в порядке приёмов и `created_at`.
- `getEntry(db, userId, entryId)` → запись или null.
- `addEntry(db, userId, input)` → `"ok" | "not_found" | "limit"`: транзакция — продукт видим, порция видима и принадлежит продукту, записей за день < 100 → insert со снимком.
- `updateEntry(db, userId, entryId, input)` → boolean: приём + количество; режим `portion` у записи без порции → false; снимок «на 100 г» не трогается.
- `deleteEntry(db, userId, entryId)` → boolean.

**`lib/foods/repo.ts`:** `getVisiblePortion(db, userId, foodId, portionId)` для `addEntry`.

**`app/(app)/diary/actions.ts`:** `addEntryAction`, `updateEntryAction(entryId)`, `deleteEntryAction(entryId)`. Каждый: `requireUserId()` первой строкой → zod (id из bound-аргументов проверяются заново) → `getUserToday` для проверки даты → репозиторий → `notFound()` при отказе; ошибки полей — `FormState`. Успех → редирект на день записи: `/` для сегодня, `/?date=…` для прошлых.

## Экраны (mobile-first 375 px, тексты из `ru.diary`, тап-зоны ≥ 44 px)
Каждая страница — `<Suspense>` + Content; загрузка, ошибка (`error.tsx` группы), пустое состояние. Чужое, несуществующее или кривой `date` → `notFound()`.

| Экран | Содержание |
| --- | --- |
| `/` (`?date=YYYY-MM-DD`) | шапка `←` · «Сегодня» / «Вчера» / «9 окт, пт» · `→` (неактивна на сегодня; тап по дате прошлого дня → сегодня). Карточка итогов: «1240 / 2100 ккал», «осталось 860» или «перебор 120» (красным), четыре полоски ккал/Б/Ж/У «съедено / норма». Четыре блока приёмов: заголовок + ккал приёма, строки «Гречка · 2 шт (120 г) · 412 ккал» → правка, «+ Добавить». Внизу — ссылки Продукты, Норма, Профиль и «Выйти». Нет нормы → `/onboarding` |
| `/diary/add?date=…&meal=…` | «Обед · 11 окт», `BackLink` на день, `FoodSearch` с фокусом; пусто → «Мои продукты»; ничего не найдено → «Добавить свой продукт». Ссылки ведут на шаг количества |
| `/diary/add/[foodId]?date=…&meal=…` | название, «343 ккал на 100 г»; чипы приёма (по умолчанию из URL); если есть порции — переключатель «Граммы \| Порции»; граммы — поле `inputMode=decimal` с фокусом; порции — список «1 шт · 60 г · 94 ккал» (ккал считает сервер), выбранной — количество с −/+ и полем; «Добавить» |
| `/diary/entries/[id]/edit` | название; чипы приёма; количество: порции снимка (−/+) или граммы, переключение на граммы; «Сохранить»; «Удалить» с подтверждением в два тапа |

**Переиспользование:** `FoodList` получает необязательный `hrefFor(item)` (по умолчанию `/foods/{id}`); `FoodSearch` пробрасывает его. Поведение `/foods` не меняется.

## Тесты
- **unit:**
  - `lib/nutrition.test.ts` (первыми): гречка 343 ккал × 150 г = 514,5 ккал; Б/Ж/У тем же способом; 0 г → нули; 60 г × 1,5 = 90 г; сумма пустого списка = нули; сумма трёх записей; прогресс с перебором (`remaining < 0`, `share > 1`) и ровно в норму; `RangeError` на минус и NaN;
  - `lib/date.test.ts`: «сегодня» в `Asia/Almaty` при 2026-10-10T20:30Z = 2026-10-11, в `UTC` = 2026-10-10; `addDays` через конец месяца, года и 29 февраля; невалидный пояс → false;
  - `lib/format.test.ts`: `formatAmount`, `formatDayLabel` (сегодня, вчера, тот же год, прошлый год);
  - `lib/diary/schema.test.ts`: граммы с запятой, пределы граммов и количества, дата в будущем и до 2000 → отказ, неверный `meal`, неверный uuid.
- **db** (`lib/diary/repo.db.test.ts`):
  - добавление по граммам и по порции (снимок названия, «на 100 г», порции, граммы = количество × граммы порции);
  - снимок не меняется после правки и переименования продукта и после удаления порции;
  - мягко удалённый продукт остаётся в дневнике дня;
  - чужой продукт, чужая порция, порция другого продукта, удалённый продукт → `not_found`;
  - лимит записей в день → `limit`;
  - день другого пользователя не виден; правка и удаление чужой записи → false;
  - правка количества порций, переход на граммы, смена приёма; режим `portion` у записи без порции → false.
- **В конце:** субагенты reviewer, security-reviewer (новые server actions и cookie `tz`), ui-checker (375 и 1280 px) — во встроенном браузере приложения: Playwright MCP в этой сессии не подключён (`.claude/.mcp.json` не читается, перенос в корневой `.mcp.json` — в открытые вопросы).
