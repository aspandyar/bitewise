# API и безопасность
- Каждый route handler / server action: проверка сессии первой строкой; без сессии → 401.
- Доступ к объекту — только если его user_id совпадает с сессией (иначе 404, не 403).
- Входные данные — zod; ответ — только нужные поля, без внутренних id других пользователей.
- Rate limit на auth и AI-эндпоинты.
- Никаких секретов в логах и ответах об ошибках.
- Исключение — `GET /api/health`: без сессии, только `{ ok }`; снаружи закрыт nginx, его вызывают healthcheck контейнера и `release.sh`.
- Server action, который создаёт строку, читает `requestId` (`readRequestId`) и при повторе возвращает уже созданное (ключ для другой цели — отказ); переключатели отправляют нужное состояние; удаление, которое ничего не нашло, ведёт туда же, куда успешное, — в том числе для чужого или несуществующего id: это не раскрывает существование объекта, поэтому вместо 404 (#95).
- Server action, который получает форму, берёт пользователя через `requireActionUser(formData)`, а не `requireUserId()`: форма, отправленная под другим аккаунтом (повтор после смены входа), ничего не пишет (#107). Клиентские формы ставят ключ и пользователя через `stampRequestId`. Действие, которое пишет без формы (удаление, «Отменить»), берёт пользователя через `requireWriteUser()`: обе функции считают лимит записи на пользователя (#31). Исключение — действия, которыми владелец выгоняет украденную сессию («Выйти на всех устройствах», смена пароля): `requireAccountUser(formData)` без лимита записи, иначе вор, держащий лимит исчерпанным, не даст себя отозвать.
- Сброс пароля по почте (когда появится): для роли `admin` запрещён, ответ как для несуществующего email; проверять по роли из базы, не по адресу (#28). Сброс и смена пароля увеличивают `token_version` (#29).
